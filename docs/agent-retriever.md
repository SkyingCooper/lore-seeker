# Retriever Agent 设计

## 1. 模块职责

### 背景

Retriever 也叫问答 Agent，面向用户日常提问、知识库问答和对话流程处理。它既要从用户自己的知识库中检索事实，也要维护必要的会话记忆、用户偏好和长期语义记忆。

### 决策

Retriever 采用“双路检索 -> RRF 融合 -> Rerank 精排 -> 基于证据回答”的流程。问答前读取用户偏好和语义记忆，问答后按规则写入情景记忆、用户偏好和语义记忆。用户原始描述中的 `zl_*` 表名按当前项目全局命名统一为 `zr_*`。

对应代码：

- `backend/agents/retriever.py`
- `backend/api/v1/knowledge.py`
- `backend/core/embedding_router.py`
- `backend/core/llm_router.py`

### 实现要点

核心职责：

- 处理用户日常对话和流程类问题。
- 理解用户提问，判断检索意图。
- 对 `knowledge_chunks` 执行关键词检索和向量语义检索。
- 使用 RRF 融合双路结果。
- 必要时调用 Rerank 模型筛选 Top-K 证据片段。
- 基于证据生成回答，并返回来源。
- 写入情景记忆、用户偏好和语义记忆。
- 将当前会话上下文和语义记忆缓存到 Redis。

非职责：

- 不负责创建或拆解搜索任务，该职责属于 Planner。
- 不负责执行搜索和爬虫，该职责属于 Searcher。
- 不负责整理搜索结果和生成报告，该职责属于 Organizer。
- 不允许跨用户检索知识切片。

### 验收标准

- 用户只能检索自己任务生成的知识切片。
- 回答必须可追溯到命中的知识切片或明确说明知识不足。
- 对话后需要记录的记忆、偏好和缓存状态有明确写入规则。

## 2. 处理对话

### 背景

用户提问可能是知识问答，也可能是流程咨询、偏好表达、情绪表达或对上轮回答的反馈。Retriever 需要先理解问题类型，再决定是否检索、是否回答、是否记录记忆。

### 决策

Retriever 先做意图理解，再进入检索或对话处理。意图不清时不强行检索，转入大模型澄清流程。

### 实现要点

1. 处理对话

1.1 与用户沟通，处理流程问题。

1.1.1 用户询问系统怎么用、任务状态、报告位置、知识库入口等流程问题时，优先基于系统上下文回答。

1.1.2 流程问题不一定触发知识库检索。

1.2 理解用户的日常提问，从数据库中检索相关信息并生成回答。

1.2.1 理解用户提问，确定检索意图。

1.2.2 判断用户问题是否需要知识库证据。

1.2.3 如果需要检索，进入双路检索流程。

### 验收标准

- 系统流程问题可以直接回答，不强制走知识库检索。
- 知识问答必须进入用户隔离后的检索链路。
- 意图分类置信度低于阈值时，不返回伪确定答案。

## 3. 双路检索

### 背景

单一向量检索容易漏掉精确关键词，单一关键词检索又难覆盖语义相近表达。Retriever 需要同时支持关键词检索和向量语义检索。

### 决策

采用 BM25 关键词检索和 pgvector 语义检索双路召回。两路各返回 Top-20，再用 RRF 融合为 Top-30 候选池。

### 实现要点

1. 执行双路检索

1.1 关键词检索（BM25）

1.1.1 对用户问题进行分词。

1.1.2 在 `knowledge_chunks` 的文本字段中检索。

1.1.3 检索字段优先级：

- `summary`：用于快速匹配和预览。
- `content`：用于完整正文匹配。
- `section_title`：用于章节标题匹配。

1.1.4 返回 Top-20。

1.2 向量语义检索

1.2.1 调用 embedding provider 获取用户问题向量。

1.2.2 在 `knowledge_chunks.embedding` 上执行 pgvector 检索。

1.2.3 `knowledge_chunks.embedding` 基于 `summary` 生成，因此查询向量也与摘要向量空间对齐。

1.2.4 向量索引必须使用 HNSW。

1.2.5 返回 Top-20。

1.3 用户隔离

1.3.1 所有知识检索必须走 ownership join：

```text
knowledge_chunks.report_id
  -> reports.task_id
  -> search_tasks.user_id
  -> current_user.id
```

1.3.2 SQL 必须包含：

```sql
JOIN reports r ON r.id = kc.report_id
JOIN search_tasks st ON st.id = r.task_id
WHERE st.user_id = :user_id
  AND st.deleted_at IS NULL
```

1.4 结果融合

1.4.1 使用 RRF 融合 BM25 和向量检索结果。

1.4.2 融合后得到 Top-30 候选池。

1.4.3 同一个 `knowledge_chunks.id` 在两路结果中重复出现时合并为一条候选，并保留两路分数。

### 验收标准

- BM25 和向量检索都必须经过用户隔离。
- 两路各自最多返回 Top-20。
- 融合候选池最多 Top-30。
- 候选必须保留 `chunk_id`、`report_id`、`summary`、`source_search_ids` 和分数信息。

## 4. 重排序与回答

### 背景

融合后的候选池仍可能包含相似但不够准确的片段。回答前需要挑选最匹配的证据，避免把弱相关内容塞进 prompt。

### 决策

当候选数量较多或相关性难以判断时，调用 Rerank 模型对 Top-30 候选重新打分，筛选 Top-K 证据片段。默认 K=5。

### 实现要点

1. Rerank 触发

1.1 候选数量较多时触发。

1.2 BM25 和向量结果冲突明显时触发。

1.3 需要更高精度判断时触发。

2. Rerank 执行

2.1 调用 Rerank 模型，例如千问 GTE-Rerank。

2.2 对候选池中的 30 个片段重新打分。

2.3 筛选 Top-K 片段，默认 `K=5`。

2.4 如果最高分 `< 0.5`，视为检索证据不足，触发“大模型回答条件”中的 `3.3`。

3. 生成回答

3.1 将 Top-K 片段作为回答上下文。

3.2 Prompt 必须注入用户偏好，例如回答风格、语言、长度偏好。

3.3 回答必须基于上下文，不得编造上下文外事实。

3.4 返回 `answer` 和 `sources`。

3.5 `sources` 至少包含：

- `chunk_id`
- `report_id`
- `summary`
- `source_search_ids`
- `score`
- `rerank_score`

### 验收标准

- sources 顺序与最终使用上下文一致。
- rerank score 能回传给前端用于展示。
- 最高 rerank 分数低于 `0.5` 时，不能伪装成已找到可靠答案。

## 5. 会话信息跃迁

### 背景

Retriever 在对话过程中会遇到临时事件、用户偏好和长期用户事实。这些信息不能全部混在同一张表里，需要按记忆类型进入不同存储。

### 决策

对话后按三类记忆处理：情景记忆先写 Redis、会话结束后落入 `zr_episodic_logs`；用户偏好直接写入 `zr_user_preferences`；长期语义记忆先写 Redis、会话结束后落入 `zr_semantic_memories`。当前会话、语义记忆和工作记录都需要写入 Redis。用户原始描述中的 `zl_*` 表名按当前项目全局命名统一为 `zr_*`。

### 实现要点

1. 情景记忆

1.1 记录内容

1.1.1 情景记忆是系统流水账日记，按事件类型记录每次对话和任务执行过程。

1.1.2 典型内容包括：

- 用户表达情绪，例如“我今天心情有点悲伤”。
- 用户提到某个短期上下文。
- Agent 执行任务。
- 对话或工具调用发生错误。

1.2 写入时机

1.2.1 每次对话轮次结束后，先写入 Redis。

1.2.2 对话结束后写入数据库。

1.2.3 对话结束判定规则：

- 例如 5 分钟没有下一轮对话，视为当前会话进入可归档状态。

1.3 写入表

- `zr_episodic_logs`

1.4 Redis Key

| Key | 内容 | TTL |
|---|---|---|
| `session:{user_id}:{session_id}:context` | 当前会话最近 5 轮对话 | 30 分钟 |

1.5 数据示例

```json
{
  "event_id": "uuid",
  "user_id": "xxx",
  "session_id": "xxx",
  "event_type": "user_message",
  "content": "我今天心情有点悲伤",
  "emotion_tag": "sad",
  "importance": 0.6,
  "created_at": "2026-06-02 10:00:00"
}
```

1.6 读取时机

- 用户说“我之前说过...”时回溯历史。
- 当前回答需要理解最近对话上下文时读取。

1.7 读取来源

1.7.1 第一轮对话从数据库拉取最近 5 条情景记忆，并加载到 Redis。

1.7.2 后续对话直接从 Redis 读取。

2. 用户偏好

2.1 记录内容

2.1.1 用户反馈的偏好需要记录到 `zr_user_preferences`。

2.1.2 典型内容包括：

- 用户显式表达偏好，例如“我喜欢排版简洁一点”。
- 用户隐式表达偏好，例如多次要求“短一点”“直接给结论”。

2.2 写入时机

2.2.1 用户显式或隐式表达偏好时触发。

2.2.2 每次对话轮次结束后，直接写入数据库。

2.3 写入表

- `zr_user_preferences`

2.4 数据示例

```json
{
  "pref_id": "uuid",
  "user_id": "xxx",
  "pref_type": "response_style",
  "pref_key": "format",
  "pref_value": "concise",
  "source": "explicit",
  "confidence": 0.9,
  "created_at": "2026-06-02 10:00:00"
}
```

2.5 读取时机

- 生成回答前注入 prompt，例如“用户偏好简洁，请用短句回答”。

2.6 读取来源

2.6.1 直接从数据库全量加载当前用户偏好。

2.6.2 加载后按 `confidence`、偏好类型和更新时间决定注入优先级。

3. 语义记忆

3.1 记录内容

3.1.1 长期事实和长期项目背景需要记录到 `zr_semantic_memories`。

3.1.2 典型内容包括：

- 用户长期事实，例如“用户是软件工程师”。
- 用户长期项目背景，例如“用户正在开发一个多 Agent 系统”。

3.2 读取时机

3.2.1 每轮对话前，检索与该用户相关的语义记忆。

3.3 读取来源

3.3.1 第一轮对话从数据库读取语义记忆并加载到 Redis。

3.3.2 Redis Key：

| Key | 内容 | TTL |
|---|---|---|
| `user:{user_id}:semantic` | 当前用户语义记忆缓存 | 30 分钟 |

3.3.3 数据库加载规则：

- 只加载 `confidence >= 0.6` 的语义记忆，或最近 7 天访问过的语义记忆。
- 按 `confidence` 排序。
- 每个用户最多加载 50 条。
- 必须过滤 `deleted_at IS NULL`。

3.3.4 后续对话优先从 Redis 读取。

3.4 写入时机

3.4.1 每次对话轮次结束后，调用 LLM 或规则提取“关于用户的长期事实”。

3.4.2 提取结果先写入 Redis。

3.4.3 对话结束后写入数据库。

3.4.4 对话结束判定规则：

- 例如 5 分钟没有下一轮对话，视为当前会话进入可归档状态。

3.5 写入表

- `zr_semantic_memories`

3.6 写入流程

- 按标题或段落切分。
- 保持语义完整，不截断句子。
- 支持 overlap 保证上下文连贯。
- `embedding` 基于 `summary` 生成。
- 向量索引使用 HNSW。
- 使用 `confidence` 记录记忆置信度。
- 使用 `last_accessed` 记录最近使用时间。
- 使用 `deleted_at` 做逻辑删除和淘汰。

4. 工作记录

4.1 Retriever 的工作记录需要写入 Redis。

4.2 工作记录用于记录本轮问答的执行细节，例如：

- 意图识别结果。
- BM25 检索结果数量。
- 向量检索结果数量。
- RRF 融合候选数量。
- Rerank Top-K 分数。
- 是否触发大模型回答。
- 是否写入情景记忆、偏好或语义记忆。

4.3 Redis Key 建议：

| Key | 内容 | TTL |
|---|---|---|
| `session:{user_id}:{session_id}:retriever_worklog` | 当前会话 Retriever 工作记录 | 30 分钟 |

### 验收标准

- 情景记忆只记录对话和任务事件，不替代长期事实。
- 用户偏好在回答前注入 prompt。
- 语义记忆查询必须过滤 `deleted_at IS NULL`。
- 第一轮对话从数据库预热情景记忆和语义记忆，后续轮次优先从 Redis 读取。
- 情景记忆和语义记忆在会话空闲归档后写入数据库。
- 用户偏好在对话轮次结束后直接写入数据库。
- Redis 缓存不能成为唯一持久数据源。

## 6. 调用大模型回答的情况

### 背景

Retriever 默认应基于检索证据回答，但部分场景需要大模型参与澄清、重写或解释失败原因。

### 决策

只有在意图不清、用户反馈不满意或检索证据不足时，才触发大模型增强回答流程。

### 实现要点

1. 意图不清

1.1 不明白问题含义。

1.2 意图分类置信度 `< 0.6`。

1.3 处理方式：

- 优先追问澄清。
- 不直接编造答案。

2. 用户不满意

2.1 用户说“不对”“不是这个”“重新回答”等。

2.2 处理方式：

- 读取上一轮回答和 sources。
- 分析不满意原因。
- 必要时调整检索 query 或扩大候选池。

3. 检索证据不足

3.1 无法检索到对应内容。

3.2 Rerank 最高分 `< 0.5`。

3.3 处理方式：

- 明确告知当前知识库证据不足。
- 可以建议用户创建搜索任务补充知识库。
- 不把低置信度内容包装成确定结论。

### 验收标准

- 触发大模型时有明确原因。
- 低置信度检索结果不会被当作可靠证据。
- 用户不满意场景会使用上一轮上下文做修正。

## 7. 已确认配置

### 背景

Retriever 的召回和重排序策略会影响知识问答质量，不能散落在代码中，也不能在文档里保留多套未决方案。

### 决策

检索策略统一进入 `config/retriever.yaml`。

### 实现要点

- 向量维度统一为 `1024`。
- embedding 模型统一使用千问 `text-embedding-v4`。
- 关键词检索使用 PostgreSQL `tsvector`。
- RRF 常量 `k` 抽取为配置项，默认 `60`。
- Rerank 统一使用阿里云 `qwen3-rerank` API。
- 所有向量索引统一使用 HNSW。

### 验收标准

- `backend/db/schema.sql`、SQLAlchemy model、Tool contract 和 `config/retriever.yaml` 的向量维度一致。
- RRF、Top-K、rerank 阈值修改只需要调整配置。
- Retriever 不直接写死 provider、模型名或排序阈值。
