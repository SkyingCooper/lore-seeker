# Searcher Agent 设计

## 1. 模块职责

Searcher 是执行型 Agent，接收 Planner 生成的子任务列表和搜索策略，负责检索、爬取、限流、重试、汇总搜索元数据，并将阶段性工作状态写入 Redis。

Searcher 可以使用小模型完成搜索策略判断、失败分类和结果相关性初评；只有搜索效果不满意或策略需要调整时，才升级调用大模型。

对应代码：

- `backend/agents/searcher.py`
- `backend/services/search_service.py`

## 2. 搜索模式

### 背景

不同任务需要不同采集方式：API 搜索速度快，爬虫适合用户指定站点，混合模式兼顾覆盖和深度。

### 决策

全局统一使用 `search_mode` 字段，合法值为：

| 值 | 行为 |
|---|---|
| `api` | 只调用搜索 API |
| `crawl` | 只爬取 `source_sites` |
| `mixed` | API 搜索 + 爬虫补充 |

搜索来源字段统一为 `source_sites`。

### 实现要点

Searcher 从 Agent state 读取：

```python
config = state["topic_config"]
plan = config.get("_plan", {})
queries = plan.get("search_queries", [state["query"]])
source_sites = config.get("source_sites", [])
search_mode = config.get("search_mode", "api")
```

执行规则：

- `api` 和 `mixed`：遍历 `queries` 调用 `search_api()`。
- `crawl` 和 `mixed`：当 `source_sites` 非空时调用 `crawl_sites()`。
- API 搜索携带 `source_sites` 作为站点过滤条件。
- 所有结果按 URL 去重。

### 验收标准

- `api` 模式不依赖 `source_sites` 也能返回结果。
- `crawl` 模式必须使用 `source_sites`。
- `mixed` 模式会合并 API 和爬虫结果。
- 输出结果中同一 URL 只保留一次。

## 3. 预处理

### 背景

搜索执行前需要判断是否可以复用已有知识、是否要按站点控制限流、以及如何把 Planner 子任务转换成可执行队列。

### 决策

Searcher 在正式搜索前执行预处理，优先复用已有结果；无法满足时再进入异步搜索。

### 实现要点

详细工作流程：

1. 预处理
1.1 从 Agent state 读取 `query` 和 `topic_config`。
1.2 从 `topic_config["_plan"]` 读取 Planner 生成的 `search_queries`。
1.3 从 `topic_config["_plan"]["subtasks"]` 读取结构化子任务。
1.4 当计划缺失时，回退使用用户原始 `query` 作为唯一子任务。

2. 库内复用判断
2.1 检查近期是否已有相同或相似任务结果。
2.2 如果已有库内结果能够满足用户需求，直接复用已有数据。
2.3 复用已有数据时生成复用摘要。
2.4 如果库内结果不足，继续生成搜索执行队列。

3. 站点策略准备
3.1 读取每个子任务的关键词、`source_sites`、优先级和搜索模式。
3.2 按目标来源站点对任务分组。
3.3 为不同网站加载对应搜索或爬取方案。
3.4 针对容易限流的网站设置并发数和请求间隔。
3.5 如果站点存在限流与退避规则，从配置文件读取站点策略。
3.6 如果站点策略缺失或不适用，调用模型生成新的搜索策略建议。

4. 执行队列生成
4.1 将 Planner 的子任务列表转换成可执行队列。
4.2 将队列、站点分组、并发限制和预计任务数量写入 Redis。

### 验收标准

- 相似任务可复用时不重复搜索。
- 每个目标站点都有明确的并发和间隔策略。
- Planner 子任务能被转换成可执行队列。

## 4. 异步执行

### 背景

搜索任务可能包含多个关键词和多个来源站点，需要并发执行，但必须控制站点限流、单任务超时和失败重试。

### 决策

Searcher 按搜索策略分批执行任务。并发上限为 10，单站点请求受站点策略控制，执行过程中的中间状态写入 Redis。

### 实现要点

详细工作流程：

1. 收到任务后
1.1 接收一个或多个待执行子任务。
1.2 按任务优先级排序。
1.3 按站点分组并建立执行批次。
1.4 根据任务配置选择 `api`、`crawl` 或 `mixed`。

2. 分批异步执行
2.1 并发执行时全局并发数量最多为 10。
2.2 同一网站按站点策略控制并发和请求间隔。
2.3 执行 API 搜索时附带 `source_sites` 过滤条件。
2.4 执行爬虫时按站点策略设置 User-Agent、等待策略和超时。
2.5 在 Redis 中实时更新中间状态，例如“正在解析某网站”。
2.6 每个网站任务设置超时控制，默认 1 分钟。

3. 重试与失败分类
3.1 失败时判断错误类型。
3.2 超时和 5xx 归类为可重试错误。
3.3 404 和 403 归类为不可重试错误。
3.4 可重试错误最多重试 3 次。
3.5 重试使用指数退避。
3.6 搜索或爬虫失败时记录失败分类和上下文，不吞掉错误。

4. 结果标准化
4.1 所有执行结果统一标准化为 `title`、`url`、`content`。

### 验收标准

- 全局并发不超过 10。
- 同一网站不会被高频请求打爆。
- 子任务状态能在 Redis 中实时追踪。
- 可重试和不可重试错误分类清晰。

## 5. 搜索 API 路由

### 背景

搜索服务需要支持多个提供商，并能通过配置切换。

### 决策

搜索实现放在 `search_service.py`，Agent 节点只做模式路由。

### 实现要点

配置项：

- `SEARCH_API_PROVIDER=tavily|serpapi|bing`
- `TAVILY_API_KEY`
- `SERPAPI_KEY`
- `BING_SEARCH_API_KEY`

提供商：

| 提供商 | 说明 |
|---|---|
| Tavily | 默认搜索 API，适合 AI 摘要场景 |
| SerpAPI | Google 搜索结果 |
| Bing | Microsoft Bing 搜索 |

站点过滤：

- 当 `source_sites` 非空时，API 查询添加 `site:` 条件。
- 多个站点以 OR 方式组合。

### 验收标准

- 切换 `SEARCH_API_PROVIDER` 不需要修改 Agent。
- 缺少非当前 provider 的 API key 不影响启动。
- 搜索失败时错误能被 worker 捕获并反映到任务状态。

## 6. 汇总处理

### 背景

API 搜索和爬虫会返回重复页面。Organizer 需要稳定输入，Planner 也需要知道每个子任务的执行质量。

### 决策

Searcher 在执行结束后统一汇总搜索元数据、生成搜索摘要、检查子任务完成情况，并将汇总记录写入 Redis。

### 实现要点

输出格式：

```python
[
  {
    "title": "文章标题",
    "url": "https://example.com/article",
    "content": "正文摘要或截断后的全文"
  }
]
```

去重规则：

- URL 完全一致时视为重复。
- API 和爬虫结果合并后统一去重。
- 保留第一次出现的结果，保持 API 优先、爬虫补充的顺序。

汇总字段：

| 字段 | 说明 |
|---|---|
| `subtask_id` | 子任务标识 |
| `keyword` | 执行关键词 |
| `source_site` | 目标来源 |
| `duration_ms` | 搜索耗时 |
| `retry_count` | 重试次数 |
| `result_count` | 结果数量 |
| `expanded_keywords` | 扩展关键词 |
| `error_type` | 失败分类 |
| `summary` | 搜索摘要 |

详细工作流程：

1. 汇总搜索元数据
1.1 汇总每个子任务的搜索耗时。
1.2 汇总每个子任务的重试次数。
1.3 汇总每个子任务的结果数量。
1.4 汇总关键词扩展和搜索策略调整情况。
1.5 每个子任务生成一条 `search_history`。
1.6 为每条 `search_history` 生成搜索摘要。

2. 检查完成状态
2.1 检查所有子任务是否都已完成。
2.2 完成状态包括成功和失败。
2.3 所有子任务结束后，生成整体搜索摘要。

3. 汇总记录落地
3.1 将汇总记录写入 Redis。
3.2 将标准化、去重后的搜索结果写入 state。
3.3 通知 Planner 搜索阶段完成。

### 验收标准

- 输出结果字段稳定。
- 同一 URL 不重复进入 Organizer。
- 空结果能被后续节点识别并给出失败或空报告状态。
- 每个子任务都有一条搜索历史记录。
- Redis 中能查看完整搜索汇总。

## 7. 执行后评估

### 背景

搜索结束后需要判断结果是否满足用户需求。结果太少、相关性低或用户描述存在隐含需求时，需要补充搜索策略。

### 决策

Searcher 对搜索内容做初次评估。默认使用轻量模型或规则判断；当搜索效果不满意时，调用大模型改进搜索策略。

### 实现要点

评估内容：

- 搜索结果是否符合用户需求。
- 前几条结果的主题相关性。
- 是否遗漏用户 description 中的隐含需求。
- 是否需要补充搜索词或更换来源站点。
- 是否存在实时性要求。

触发大模型改进搜索策略的条件：

1. 关键词太宽泛，例如 `AI`。
2. 前 5 条结果相关性低于 30%。
3. 用户 `description` 有隐含需求，例如“关注安全”。
4. 任务有实时性要求。
5. 多个子任务无结果或结果明显偏题。

大模型调用目标：

- 说明此次搜索效果不满意的原因。
- 生成更具体的子关键词。
- 调整目标来源。
- 给出新的搜索策略。
- 将改进建议写入 Redis，交回 Planner 判断是否补搜。

### 验收标准

- Searcher 能给出结果相关性初评。
- 搜索效果差时能产出明确改进策略。
- 改进策略不会直接覆盖 Planner 原始目标，只作为下一轮搜索建议。

## 8. 爬虫策略

### 背景

有些资料需要抓取指定页面正文，搜索 API 摘要不足以支撑报告生成。

### 决策

爬虫使用 Playwright 无头 Chromium 渲染页面，再用 BeautifulSoup 提取文本。

### 实现要点

- 每个任务最多使用 5 个 `source_sites`。
- 页面超时时间 15 秒。
- 等待策略为 `domcontentloaded`。
- 提取正文后截取前 3000 字符。
- 爬虫开关和 User-Agent 来自 `backend/config.toml`。

### 验收标准

- 爬虫能处理 JS 渲染页面。
- 超时或单站失败不应阻塞整个任务。
- 输出格式与 API 搜索结果一致：

```python
{
  "title": "标题",
  "url": "https://example.com",
  "content": "正文摘要或截断文本"
}
```
