# 系统总览

## 设计目标

Lore Seeker 的核心目标是将"主题搜索 → 知识整理 → 持久检索"这条链路自动化。用户描述一个主题，系统完成其余所有工作，最终沉淀为可持续问答的个人知识库。

## 数据流

```
用户提交查询
    │
    ▼
FastAPI 创建 SearchTask 记录（status=pending）
    │
    ▼
Celery 异步执行 Agent 图
    │
    ├─ Planner：拆解子查询，预判章节结构
    ├─ Searcher：调用搜索 API / 爬虫，返回原始结果
    ├─ Organizer：过滤、编排，生成 Markdown + TOC
    └─ Quality Check：评分，不通过则反馈给 Organizer 重试
    │
    ▼
knowledge_service：Markdown 切片 → 向量化 → 写入 pgvector
    │
    ▼
SearchTask status=done，Report 记录写入
    │
    ▼
前端轮询到 done，展示报告
```

## 关键设计原则

- **异步解耦**：Agent 流水线通过 Celery 异步执行，API 层只负责触发和状态查询，不阻塞
- **配置分层**：非敏感配置在 `config.toml`（可进 git），secrets 在 `.env`，环境变量优先级最高
- **存储三层**：关系层管元数据，向量层管语义检索，缓存层管任务队列
- **Agent 单一职责**：每个 Agent 只做一件事，通过 LangGraph 状态对象传递上下文

## 2025-05-27 — 初始架构设计

**背景**：项目从零开始，确定整体技术选型和模块划分。

**决策**：
- 选用 LangGraph 而非 LangChain LCEL，因为需要有向图 + 条件边（质检重试循环）
- 选用 pgvector 而非独立向量数据库（Qdrant/Weaviate），减少运维复杂度，PostgreSQL 一库两用
- 选用 Celery + Redis 而非 FastAPI BackgroundTasks，支持 worker 独立扩展和任务重试

**放弃的方案**：
- LlamaIndex 作为主编排框架：灵活性不如 LangGraph，难以实现质检循环
- 独立向量数据库：增加一个服务依赖，pgvector 对当前规模足够

**影响范围**：全局架构
